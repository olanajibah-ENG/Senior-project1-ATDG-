1. الخطط الثلاث والتقييم المبدئي

انطلق العمل من ثلاث خطط مكتوبة، كل وحدة مبنية على أوراق علمية:

الخطةالأوراقالفكرة الأساسية
تحسين مسار Code vs DocDocPrism (ISSTA 2026)، METAMON (arXiv 2025) تقسيم التوثيق وربط كل جزء بعنصره، تحليل دلالي بالـ LLM، تصنيف LCEF الرباعي، تجاهل الـ Under-Promise، درجات ثقة وعتبات قرار، و Fallback عند فشل الـ LLM.
تحسين مسار Code vs CodeAexPy (ISSRE 2022)، Safer Builders (MSR 2026)، NPM Breaking Changes (TOSEM 2025) مقارنة التوقيع والجسم دائماً، مصفوفة قرار (Signature × Body)، استدعاء الـ LLM بس للتغييرات السلوكية، تصنيف خطورة بمستويات AexPy الأربعة.
خطة إثبات الدقةDocPrism، Cascade (FSE 2026)، C4RLLaMA قياس Precision و Recall و Specificity و F1 و PFP و Flag Rate على عينات جاهزة، ومقارنة النظام القديم مع الجديد.

أهم الملاحظات على الخطط قبل التنفيذ

1. أساس مشترك ناقص: جسم الدالة خطة Code vs Code قائمة على "افحص الـ Body دائماً"، وخطة الإثبات معتمدة على Cascade يلي تناقضاتها سلوكية جوا الجسم. بس ‎MethodDetail‎ ما كان فيه أي حقل للجسم، والـ processors ما كانت تستخرجه. لهيك صار هاد الخطوة 1.
  • Code vs Doc ما فيه LLM أصلاً: كله regex بـ ‎code_doc_consistency.py‎. والخطة كانت بتقترح تعديل ‎semantic_analyzer.py‎، وهاد ملف Code vs Code. القرار: محلّل دلالي منفصل للتوثيق.
  • ما منلغي المطابقة القديمة كلها: فحوصات التوثيق المنظّم (متل raises مقابل return None) دقيقة وبدون تكلفة، فبتضل طبقة أولى و Fallback.
  • الدوال غير الموثّقة: حالياً كل وحدة بتنحسب تناقض، وهاد مصدر رئيسي للإنذارات الكاذبة. القرار: بتنتقل لإحصائيات التغطية.
  • بناء "قبل وبعد لكل hunk": فكرة Safer Builders معمولة للـ commits، ونظامنا بياخد نسختين كاملتين. القرار: مؤجّلة.
  • خطة الإثبات: بتحتاج محوّل (adapter) من صيغة عينات DocPrism و Cascade لصيغة مدخلات نظامنا، وهاد مش مذكور بالخطة.

4. الخطوة 1: استخراج جسم الدالة ومعلوماتها

commit: ‎84e5ac5‎ — تقرير الاختبارات: ‎core_ai/tests/reports/step1_method_details.md‎

4.1 المشكلة

  • كل دالة كان ينحفظلها: الاسم، والتوقيع كنص، والـ visibility، و abstract/constructor. بدون جسم.
  • معلومات المعاملات ناقصة: بايثون ما بيسجّل القيم الافتراضية ولا ‎*args‎ و ‎**kwargs‎. جافا بتطلّع المصفوفة ‎Object‎ وبتضيّع الـ varargs.
  • دوال ضايعة من المخطط: دوال ‎async‎ بالبايثون، والـ constructors بالجافا.

4.2 الحقول الجديدة لكل دالة

الحقلالمحتوى
‎body‎جسم الدالة بدون تعليقات وبدون docstring (حد أعلى 20 ألف حرف)
‎body_hash‎بصمة للجسم بعد التطبيع: التعليقات والمسافات ما بتغيّرها، وتغيير المنطق بيغيّرها. بتنحسب على الجسم الكامل.
‎parameters‎لكل معامل: name و type و default و kind (positional_only, positional_or_keyword, keyword_only, var_positional, var_keyword)
‎return_type‎نوع الإرجاع المكتوب
‎decorators‎متل ‎@staticmethod‎ و ‎@property‎ و ‎@Override‎
‎docstring‎docstring بالبايثون، أو Javadoc/JSDoc (‎/** */‎)، أو C# (‎///‎)
‎is_async‎ و ‎line_start‎ و ‎line_end‎معلومات إضافية
قرار تصميمحقل ‎signature‎ القديم ضل حرف بحرف متل ما هو، لأنه الواجهة الأمامية و ‎FingerprintBuilder‎ بيعتمدوا عليه. المعلومات الصحيحة صارت بالحقول الجديدة.

4.3 الملفات المعدّلة

الملفالتعديل

4.4 مثال: البصمة

النسخة Aالنسخة B
def get(self, uid):
    """Return the user."""
    # lookup
    return self.store.get(uid)
 
def get(self, uid):
    """Fetch the user."""
    return   self.store.get( uid )  # trailing

10. الخطوات الجاية

الخطوة 3: تقسيم التوثيق (DocSplitter)

بدل ما ينبعت التوثيق كله دفعة وحدة، منقسّمه لأجزاء ومنربط كل جزء بالكلاس أو الدالة يلي بيحكي عنها. هاد أساس فكرة DocPrism إنه كل دالة بتنقارن بالتوثيق تبعها بس. قبل التطبيق، منفحص شكل التوثيق يلي بيولّده النظام فعلياً، لأنه التقسيم معتمد عليه.

بعدها

  • الخطوات 4–6: prompt مخصص، ومحلّل دلالي للتوثيق مع Fallback وعتبة ثقة، والربط مع نقل الدوال غير الموثّقة لإحصائيات التغطية.
  • الخطوات 7–11: مقارنة التوقيع والجسم، ومصفوفة القرار، وتصنيف الخطورة، وتقليل استدعاءات الـ LLM.
  • الخطوات 12–14: التقييم على DocPrism و Cascade، وجدول القديم مقابل الجديد.
