1. الفكرة باختصار

المشروع فيه قسمين لكشف المشاكل:

  • Code vs Doc: هل التوثيق بيوصف الكود صح؟
  • Code vs Code: بين نسختين من الكود، شو تغيّر؟ وهل التغيير بيكسر يلي عم يستعملوا الكود؟

عم نحسّن القسمين خطوة خطوة حسب خطط مبنية على أوراق بحثية (DocPrism و METAMON للتوثيق، و AexPy و NPM و Safer Builders للكود). وبعد كل خطوة منقيس على بيانات الأوراق نفسها، مش على بيانات عملناها نحنا. وبتوجيه الدكتور، اخترنا ورقة وحدة لكل قسم: CASCADE للتوثيق، و NPM للكود.

3. Code vs Doc على بيانات CASCADE

البيانات والمقياس

بيانات CASCADE فيها 71 دالة جافا توثيقها متناقض مع الكود، ومع كل وحدة نفس الدالة بعد ما تصلّح التوثيق. قسّمناها: 25 زوج للتطوير (منفتح أخطاءه)، و46 زوج للاختبار (أرقام بس، بالمحطات المهمة).

4. Code vs Code على بيانات NPM

البيانات

  • ورقة NPM (النسخة 3، مفتوحة على Zenodo): فيها 1519 تغيير بيكسر الكود، موسومين يدوياً من المؤلفين بـ 131 مشروع JavaScript/TypeScript. ثلثينهم تقريباً تغييرات سلوكية (نفس التوقيع بس الشغل تغيّر)، والباقي بنيوية (حذف، إعادة تسمية، تغيير توقيع).
  • الكود: الورقة ما فيها الكود نفسه، فنزّلناه من GitHub لكل تعديل، قبل وبعد. نزل كود 1460 تعديل من 1487.
  • أمثلة سليمة: الورقة فيها بس تعديلات بتكسر، فما في طريقة نقيس فيها الإنذارات الكاذبة. لهيك جبنا 338 تعديل عادي من نفس المشاريع ونفس الفترة، رسالتهم ما فيها أي إشارة لكسر. هدول "سليمين على الأرجح"، مش موسومين من المؤلفين.
  • التقسيم: 20% تطوير و 80% اختبار، ثابت (seed 42).

طريقة القياس

  • الوحدة هي التعديل كله، لأنه وسم الورقة على مستوى التعديل مش الملف.
  • لكل ملف كود تغيّر، منقارن النسخة قبل وبعد. والتعديل بينحسب "منبَّه عليه" إذا طلع فيه تغيير بيكسر أو إعادة تسمية أو تغيير سلوكي.
  • ملفات الاختبارات والأمثلة منتجاهلها، لأنها ما بتأثر على يلي عم يستعملوا المكتبة. والتعديلات يلي ما ضل فيها ملف ينفحص بتطلع من المقاييس (165 تعديل).
  • هالقياس بدون ذكاء اصطناعي، يعني الفحص البنيوي بس، وما كلّف ولا طلب.
